# MiniPlayer C++ · Qt5 多线程视频播放器

一个用 **Qt5 Widgets** 画的视频播放器，重点不是界面，而是播放器内核的三件事：

1. **多线程**：读线程 / 渲染线程分离，GUI 线程不做任何重活；
2. **缓存队列**：有界、按时长+帧数双重限流、带代际(serial)与统计；
3. **变速播放**：画面只改媒体时钟斜率，声音走 atempo 或 OLA 时域拉伸保音调。

解码后端是**可插拔**的：有完整 `ffmpeg.exe` 就用它（子进程管道），没有就用内置合成演示源，
两条路走的是**完全相同的多线程管线**，所以功能和演示效果不受影响。

## 2. 线程模型

```
                    ┌──────────────── GUI 线程（MainWindow + Player）────────────────┐
                    │  只管：发指令 / 收 QImage 画到控件 / 收统计刷新监控面板         │
                    └───────▲───────────────────────────────┬──────────────────────┘
                            │ frameReady(QImage)             │ play/pause/seek/speed
        ┌───────────────────┴──────────┐        ┌───────────▼───────────────────────┐
        │ render-video                 │        │ read-video                        │
        │  * 看队首帧 pts 与媒体时钟的差 │        │  * decoder->readVideo()           │
        │  * 等 / 出 / 丢  三选一        │◀───────│  * 队列满就阻塞（背压）           │
        │  * 空队列→缓冲态，必要时停钟   │  队列  │  * 收到 seek 请求时自己执行 seek  │
        └──────────────────────────────┘        └───────────────────────────────────┘
        ┌──────────────────────────────┐        ┌───────────────────────────────────┐
        │ render-audio                 │        │ read-audio                        │
        │  * 写 QAudioOutput            │◀───────│  * decoder->readAudio()           │
        │  * 变速：atempo 或 OLA 拉伸    │  队列  │  * 变速请求也由它执行             │
        │  * 上报"现在听到哪了"→音频时钟 │        └───────────────────────────────────┘
        └──────────────────────────────┘
```

几条刻意的设计：

* **读线程不参与任何时序判断**，只知道"搬帧"；什么时候出帧只由 `VideoRenderer` 决定。
  这样"卡了/快了/慢了"永远只有一个地方要查。
* **暂停 = 停止消费**。渲染线程停手 → 队列很快满 → 读线程被 `push()` 顶住 → 解码器也不再前进。
  背压本身就是最省事的流控，不需要额外的暂停信号链。
* **seek 与变速都路由给读线程执行**。解码器（尤其是 ffmpeg 子进程）不是线程安全的，
  谁读它谁负责改它，避免主线程和读线程同时操作同一份状态。
* 所有等待都带超时（`StoppableThread::sleepFor` / `push(timeout)`），关窗口不会卡住。

## 3. 缓存队列

`src/core/frame_queue.h`（模板，视频/音频共用）：

* **双重限流**：`maxFrames` 和 `maxDuration` 任一满足即视为满。12 帧 1080p RGB24 约 72MB，
  只看帧数会吃爆内存；只看时长又会被低帧率/高分辨率坑。
* **peek()**：渲染线程必须"先看队首帧的 pts 再决定出不出"，取出再放回会破坏时序判断。
* **代际(serial)**：`clear()` 时自增。seek 之后仍在解码途中的旧帧在 `push()` 时被直接拒收，
  从根上杜绝"上一代的帧混进新时间线"。
* **统计**：写入/取出/被拒/迟到丢帧/空队列次数/峰值，右侧监控面板实时显示；
  `empty_waits` 和 `dropped_late` 是判断"卡顿到底是生产者慢还是消费者慢"的关键指标。

参数在 `src/core/config.h`，改完重新编译即可做实验。

## 4. 变速播放

**画面侧**（`src/core/media_clock.h`）：不把 pts 除以倍速，而是**分段线性重新锚定** ——
改斜率前先用当前时间重设锚点，所以变速瞬间画面位置完全连续，不用重启解码。

**声音侧**（`src/threads/audio_renderer.cpp`）：

| 情况 | 做法 |
| --- | --- |
| 后端有 `atempo` | `ffmpeg -af atempo=...` 重建音频管道，音调、音色都不变（4x 会自动级联成 `[2,2]`） |
| 没有 atempo | 内置 `OlaStretcher`（`src/core/time_stretch.cpp`）做时域重叠相加，CPU 侧保音调 |
| 1.0x | 直通，零开销零延迟 |

OLA 实现里有两个容易踩的坑，都踩过了：

1. 合成跳距 ≠ 分析跳距时，Hann 窗的叠加不再恒为 1，必须**额外累加窗权重并归一化**，
   否则会出现周期性音量起伏（听起来像颤音）。
2. 只做固定跳距的叠加，加速时相邻两帧会因**相位差互相抵消**，波形被削平。
   实测：1.5x 音量只剩 **25%**、2x 只剩 **65%**（听感又闷又抖）。
   修法是给叠加前加一道 **WSOLA 式相似度搜索**：在 ±半个分析跳距内找一段与
   "已叠加但还没输出"的部分最同相的输入接上去。修完 1.5x / 2x 的音量增益都是 **1.00**。
   注意搜索偏移**只决定取哪一段**，输入推进量恒为分析跳距 —— 否则平均速率会被搜索带偏，时长就不准了。

## 5. 音画同步

音频是参考时钟，但加了三条保护，都是为了"宁可画面轻微不同步，也不要肉眼可见地倒回去"：

1. **设备必须先证明自己在出声**（`processedUSecs` 真的涨了）才有资格上报时钟；
2. **接管主时钟时一次性吸收起始偏移**（声卡晚启动 0.5~2 秒是常事，硬对齐等于倒带）；
3. **只有小幅漂移（<120ms）才允许音频微调画面**；中等以上偏差一律不干预画面，
   长时间（约 2 秒）完全不推进则判定声卡不可用，自动切"静音 + 画面主时钟"。

在**没有物理声卡**的机器上你会看到：状态栏主时钟始终是 `clock`，画面照常 1.0x 播放。
这是预期行为（真实有音箱的桌面上才会显示 `audio`）。

### 纯逻辑单元测试（48 项，全部通过）

`--selftest` 是集成测试：它只能告诉你"整条管线不对"，还得再猜是哪一层。
而队列 / 时钟 / 拉伸这三块是纯数据与数学逻辑，可以毫秒级、确定性地断言，
它们的 bug 又恰恰最隐蔽（少丢一代帧、变速瞬间跳一下、音量被吃掉一半），
所以单独做了一个 `miniplayer_unittest`（`tests/unit_tests.cpp`），不碰声卡和窗口：

| 分组 | 覆盖的不变量 | 实测 |
| --- | --- | --- |
| 有界帧队列（25 项） | 帧数上限、**按缓存秒数封顶**、代际拒收（seek 后旧帧不混入）、`close()` 语义、`peek()` 不出队、各项统计、**背压（满了阻塞 / pop 唤醒）**、`waitForReady` | 全部 OK |
| 媒体时钟（12 项） | 1x 按墙钟推进、**变速瞬间位置连续**、2x / 0.5x 斜率、暂停冻结与恢复、软校正只追一半、超阈值硬对齐 | 1.003x / 2.002x / 0.502x |
| OLA 拉伸（11 项） | 各倍速输出时长、**音量不被窗函数或相位抵消吃掉**、换格式后不残留旧缓冲、1x 旁路、**`flush()` 补齐尾部残留** | 时长比 0.98~1.98，音量增益 0.996~1.001 |

## 8. 已知限制

* **FFmpeg 子进程后端的 pts 靠"帧序号 ÷ 恒定帧率"推算**（`rawvideo` 管道里没有时间戳），
  对 CFR 素材准确，对 VFR 素材会有偏差；需要精确支持就得链接 `libav*`（CMake 里已留
  `MINIPLAYER_HAVE_LIBAV` 开关与探测逻辑，装上开发库即可改成进程内解码）。
* 子进程后端每次 seek / 变速都要重启管道，约 100ms 的一次性开销；进程内解码没有这个问题。
* `atempo` 单级只支持 0.5~2.0，超出范围用级联（已实现）；极端倍速叠加会略微影响音质。
* 内置 OLA 的下限锁在 **0.5x**（GUI 最慢档也是 0.5x）。再慢的话合成跳距会超过窗长，
  一帧填不满输出区间，多出来的部分只能是静音；要支持更慢就得改成多窗叠接。
* 音频设备"能打开但不出声"的判定窗口是 1.5 秒（`AUDIO_START_TIMEOUT`），
  这段时间里画面以本地时钟为准，接管后才会切成音频主时钟。

## 9. 和 Python 版的对应关系

同目录下的 `python/` 是同一套设计的 Python 实现（PyQt5），两边结构一一对应：
`MediaClock` / `FrameQueue` / `OLA` / 后端工厂 / 四线程模型 都是同名同职责。

C++ 版额外做了两处改进（Python 版没有）：
1. 音频接管主时钟时**一次性吸收起始偏移**，彻底消除了"起播时画面被拽回去"的现象；
2. 音频时钟 **只在漂移很小时才允许微调画面**，设备不可靠时自动降级，不再拖慢整体播放速率。
